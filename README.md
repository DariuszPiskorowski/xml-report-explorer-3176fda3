# XML Report Explorer

XML Report Explorer is a desktop tool for reviewing XML reports generated by test equipment. It turns individual test-step records into an interactive table, helping users locate unsuccessful steps, inspect error messages and examine the recorded expected and returned values.

Developed for an internal engineering workflow and used in diagnostic work, the application is packaged as a Windows executable through an automated GitHub Actions build.

## Purpose

Raw XML reports contain detailed information, but locating the relevant test step can require searching through a large document.

XML Report Explorer presents that information in a structured view with status summaries, filtering, searching and expandable details. Users can move from an overview of the test results to the information recorded for a particular step.

## Loading a report

Select an XML file or drag and drop it into the application.

The parser reads individual `AtomicTestStep` elements. It reports an error when the XML is malformed or when no supported test-step elements are found.

The application is designed for the report structure used in the original testing workflow. It is not a general-purpose viewer for arbitrary XML documents.

## Results table

Each test step is displayed as a row containing:

- Step ID
- Recorded status
- Step name
- An indicator showing whether an error message is present
- Returned value
- Expected value
- Service method
- Error message

Click a row to expand its details, including:

- Description
- `ATS_Id` and `TST_Id`
- Timestamp, time point and elapsed time
- Evaluation method and client method
- Expected-value variable
- Full service method and service-method variables
- Full error message, when present

Missing field values are displayed as empty placeholders.

## Finding relevant steps

### Status summaries and filters

Summary cards show the total number of steps and the counts for each recognised status. Selecting a card filters the table to that status.

The parser maps report status codes as follows:

| Code | Status |
| --- | --- |
| `0` | Unknown |
| `1` | Running |
| `2` | Pass |
| `4` | Warning |
| `8` | Skipped |
| `16` | Fail |

Unrecognised codes are displayed as `Unknown`.

### Search

The search field checks the step ID, name, description, service method, error message, returned value and expected value.

Search can be combined with a status filter to narrow the displayed results.

### Sorting and table layout

Users can sort by status or error text and switch between ascending and descending order.

Status sorting uses a diagnostic priority order: Fail, Warning, Running, Unknown, Skipped and Pass. When sorting error text, empty error fields remain at the end.

Column widths can be adjusted by dragging their boundaries. A sticky table header keeps column labels visible while scrolling.

### Visual highlighting

Rows are highlighted when a step has a Fail status, contains an error message or includes an application-specific CAN write error marker in its returned value.

This helps draw attention to potentially relevant steps without changing the status recorded in the source report.

Light and dark interface themes are available.

## Interpretation of results

The application displays information recorded by the test system. Expected and returned values are presented together for inspection, but the viewer does not independently evaluate their equality or calculate a new Pass or Fail result.

A highlighted row identifies information worth examining; it does not automatically establish the root cause of a failure.

## Local file processing

The selected XML file is read and parsed within the application. Its contents are not uploaded to a report-processing server.

Report data is held in the current application session. The viewer does not modify the original XML file.

Use **Upload another file** to replace the current report.

## Windows executable and automated builds

The repository includes a manually triggered GitHub Actions workflow named **Build XML Log Viewer exe (Tauri)**.

The workflow:

1. Checks out the repository and prepares Node.js.
2. Installs dependencies and builds the frontend with Vite.
3. Verifies that the frontend entry file exists in `dist/client`.
4. Prepares Rust, the Windows x86-64 target and the Tauri CLI.
5. Builds the Windows executable with `--no-bundle`, without creating an installer.
6. Checks that an executable was produced and meets the configured minimum-size check.
7. Uploads the executable as the `XML-Log-Viewer-exe` artifact.

This separates the development environment from end-user delivery. Users receive the compiled Windows application rather than having to install the frontend and Rust development toolchains.

The desktop application is named **XML Log Viewer** and opens in a resizable window.

## Technology

- **React and TypeScript** for the interface and report-processing logic
- **DOMParser** for reading XML documents
- **TanStack Router** for application routing
- **Tailwind CSS** for styling
- **Vite** for frontend builds
- **Tauri and Rust** for Windows desktop packaging
- **GitHub Actions** for automated builds and artifact delivery
